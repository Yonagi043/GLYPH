## 四、最终成品

交付一个首先能在用户 macOS 本机完整运行、以后可以迁移到持续在线服务器的中文单研究者系统。系统必须形成以下完整闭环：

1. 平台数据采集与定时调度；
2. 数据库存储、失败治理与全过程审计；
3. 在界面中配置研究对象、查询、语言、平台、时间窗口和运行频率；
4. 单人人工审核工作台；
5. 社会叙事分析看板及证据下钻；
6. 数据、分析结果和研究产物导出；
7. 数据备份与恢复；
8. 任务状态、错误、配额、成本和系统健康监控。

不要把 CLI、静态文件集合、接口样例、fixture 演示或只有展示效果的页面称为最终成品。最终交付必须能由用户实际启动、配置、采集、审核、分析、导出和维护。

首版产品仍是中文单研究者系统。不得为了未来双编码而建设账号系统、组织、权限或多租户。数据层和导入/导出不得阻碍未来增加第二编码员；研究 release 的双编码要求与首版产品的单用户形态是两个不同层次。

## 五、不可偏离的研究核心

本系统属于“文化—历史叙事线”，不是全网流量监控器、舆情热度工具或自动审美判定器。

本线只回答：

- 哪些明确的文字系统、脚本、书体、字体或已知字标对象，在有界平台、语言、时间窗、查询和品牌场景中，与哪些评价表达共同出现；
- 这些表达由品牌方、设计机构、设计媒体、设计师/创作者、研究者还是普通用户提出；
- 表达是肯定、否定、混合、描述、反例还是不明确；
- 同一叙事在不同来源和平台中如何被观察到；
- 这些观察能否转化为其他研究线中的可检验假设。

本线不直接回答：

- 全网真实流量、真实曝光或推荐算法效果；
- 公众总体偏好、总体认可度或跨平台总体占比；
- 某种文字、书体或字体天然具有某种意义；
- 字体或文字导致高级感、现代感或偏好的因果效应；
- 叙事的历史起源，除非另有档案和来源链证据。

以下判断是不可违反的硬约束：

1. 搜索命中不是研究相关性通过。
2. scope 的目标对象不是条目中已经确认的对象事实。
3. 关键词或评价词命中不是叙事成立。
4. 视频标题、频道简介、创作者自述、顶层评论和回复不是同一种观察单位。
5. 发布者营销用词是“生产者自述”候选，不是普通用户采用或公众共识。
6. 技术问答、泛称赞和无对象的情绪表达不能因父内容属于某 scope 自动进入叙事分析。
7. 父视频语境可以辅助理解评论，但不能替代该评论与对象之间的可核查关系。
8. `relevanceLanguage`、模型语言检测或脚本检测只是候选信号，不是人工确认语言。
9. 频道名称、简介中的 `official`、`design`、`studio` 等词只能生成提示，不能自动写入 `author_role` gold 标签。
10. unknown、缺失、排除和零结果都是合法结果，不得用猜测填满字段。
11. 不得扩展 object map 来挽救一个错误的宽泛查询，例如不得把 `logo_design` 注册成研究对象以合理化泛 logo 教程样本。
12. 未取得视频转录时，只能声称分析了标题、描述和 API 可见元数据，不能声称分析了视频内容。
13. 视频线程内的多条评论存在聚类，不能不加说明地当作彼此独立的公众样本。
14. 只有 `human_verified` 可进入本机主分析；只有满足 release 质量闸门的记录才可进入研究发布物。
15. 合法的零条 `human_verified` 比伪造一条研究闭环更正确。

## 六、现有协议与统一模型

现有 social narrative 协议、schema、稳定 ID、SHA-256、manifest、registry、失败记录、人工确认规则和分析指标是系统的研究基础。

所有平台数据必须进入现有统一模型，优先复用并扩展：

- `social_observation`
- `social_run_manifest`
- query/source registries
- normalize、validate、summarize、project 流程

不得为每个平台建立互不兼容的数据、审核、分析或展示路径。

只有确认现有 schema 无法表达必要的跨平台事实时，才允许对 frozen schema 做最小扩展。扩展前必须：

1. 写明无法表达的具体事实；
2. 给出至少一个真实或 fixture 反例；
3. 说明为什么内部数据库表、运行 manifest、source registry 或派生 artifact 不能表达；
4. 得到用户对实质研究协议改变的明确确认；
5. 同时更新 schema、迁移、验证器、fixture、契约测试和文档。

内部 SQLite 表可以为工作流增加筛选事件、独立编码、裁决、质量报告和查询版本，但这些内部表不得绕过 frozen 输出协议。

## 七、查询、筛选、编码和分析的强制分层

### 7.1 Query 必须不可变

- 一个 research scope 可以关联多个 query；
- 一个 query 只能代表一个精确平台查询和一个预登记查询族；
- query 至少记录查询族、探索/确认阶段、语言、精确查询、排序、时间窗、各层配额、词表版本、规则和配置哈希；
- query 创建后只读；修改必须生成新 query ID，并用 `supersedes_query_id` 关联；
- run 必须引用执行时的不可变 query 快照；
- 旧 evidence/export 不能联查后来被修改的 query；
- 不得把多个研究含义不同的关键词无结构地拼成一次宽泛 OR 搜索后视作一个确认查询。

最低查询族仍为：

1. 对象 + 评价词；
2. 对象 + 品牌品类；
3. 评价词 + 品牌品类。

探索运行可发现别名、误命中和新词，但不得产生确认性主结论。确认运行只能使用人工审定并冻结的 query、object map 和 codebook。

### 7.2 规范化不得制造研究事实

- API 返回首先是采集到的 item/observation；
- 规范化器只转换可观察事实，不负责确认对象、评价、立场、角色或机制；
- scope 目标对象不得无条件复制到 observation 的 `object_type/object_label`；
- 自动规则、语言工具或模型输出必须进入独立筛选记录或建议字段；
- 自动结果不得伪装成 `human_verified`，不得覆盖 raw evidence。

### 7.3 筛选与人工编码必须分开

筛选层回答“是否值得进入编码队列”，人工编码层回答“这条证据实际表达了什么”。

筛选结果至少区分：

- `include`
- `exclude`
- `uncertain`

筛选必须保存规则版本、命中信号、工具版本、时间和决定理由。机器可排序或建议，但最终对象、评价词、立场、证据片段和来源角色必须由人确认。

### 7.4 Codebook 和 object map 必须运行时强制

- Web 审核不能允许任意自由字符串直接进入 gold；
- 对象和规范评价词必须来自运行时加载并哈希的 registry；
- 原文词形与规范代码分开保存；
- 新词只能进入下一探索版本，不能在确认运行中途静默加入；
- registry 缺失、哈希不符或版本不明时，阻止确认运行和主分析。

### 7.5 单人产品与研究 release 分层

- 首版 UI 保持单研究者，不新增多用户认证；
- 单人 `human_verified` 可用于验证本机审核到分析的产品闭环；
- 需要对外报告比较性研究结论或进入正式 research release 时，必须满足 frozen 协议规定的独立双编码比例和一致性门槛；
- 第二编码员可以通过未来的独立导入/导出或轻量并行记录完成，不要求当前建设完整协作平台；
- 两次连续修改同一 observation 的审核历史不是双人独立编码；
- 裁决不得删除或覆盖原始编码。

### 7.6 主分析必须有机械闸门

本机主分析至少要求 `annotation_status == human_verified`。

研究 release 和比较性结论还必须检查：

- run 是 confirmatory；
- query 不可变且哈希匹配；
- object map/codebook 版本匹配；
- 记录通过相关性筛选；
- 语言和来源角色达到相应人工确认要求；
- 双编码比例和字段级一致性达到协议门槛；
- 分母和探索性标记满足协议；
- governance/release decision 允许使用。

不得用平均 Jaccard 冒充 Krippendorff's alpha。多标签术语需按冻结代码分别转为二元判断或使用预先说明的适当可靠性方法。证据片段一致性需单独定义，不能与 nominal 标签合成一个数字。

## 十九、运行与研究质量要求

每次采集必须具备：

- 稳定来源标识与可追溯 raw evidence；
- 增量游标、幂等写入和重复检测；

- 平台级覆盖边界说明；
- 删除或不可用内容的治理路径；
- 配额、成本策略版本和逐请求记录；
- 搜索、筛选、规范化、审核和分析的逐层计数。

YouTube 额外必须记录：

- `relevanceLanguage` 仅为排序提示；

## 二十、强制记录与文档纪律

文档是研究证据的一部分，不是开发结束后的补写附件。

### 20.1 开始前

- 读取已有记录，避免重复调研、重复真实请求和重复修复；
- 在当前里程碑工作记录中写明日期、当前状态、基线、目标切片和已知风险；
- 若已有同主题工作记录，更新它；若主题确实新且需要长期追溯，再新建文档；
- 不为每个小动作创建新文件，不制造互相矛盾的报告堆。

### 20.2 工作中

每完成一个经过验证的实质切片，及时更新当前里程碑工作记录，至少写明：

- 做了什么；
- 为什么属于当前里程碑；
- 修改了哪些控制点；
- 执行了什么验证及结果；
- 对研究口径、数据迁移和旧运行有什么影响；
- 下一步最小动作；
- 是否需要用户手动操作或确认。

遇到以下情况必须立即更新或新建持久记录，不能只留在聊天中：

- 外部官方 API、配额、许可或条款事实变化；
- 发现会改变研究有效性的设计错误；
- 作出 schema、查询、抽样、编码或 release 口径决定；
- 否决一个看似可行但会导致偏航的方案；
- 真实运行发生、失败、被降级或被判定为 engineering-only；
- 数据迁移改变历史读取方式；
- 里程碑完成定义的某一项被阻塞。

### 20.3 文档格式

新的状态或决策文档必须包含：

```text
标题
版本
日期
状态
适用里程碑
是否替代/被替代
事实证据
决定与理由
验证结果
限制与未完成项
下一步及批准门槛
```

外部事实必须附官方 URL、核验日期和适用版本。动态引用量、配额、价格和维护状态必须标明快照日期。

### 20.4 结束时

- 更新运行手册中受影响的启动、升级、迁移、备份或故障处理步骤；
- 将过时文档在顶部标记为过时并链接替代记录，不删除历史；
- 里程碑报告只写已经验证的事实，不把计划写成完成；
- 报告命令、结果计数、真实运行 ID、数据边界和降级项；

## 二十一、防偏航检查

每次准备新增功能、依赖、表、字段、页面、平台或真实请求前，必须回答：

1. 它直接对应当前里程碑哪一条完成定义？
2. 它解决的是研究有效性、产品闭环还是可审计性中的哪一个具体缺口？
3. 现有协议、表或工具为什么不能满足？
4. 最小实现和最窄验证是什么？
5. 它是否会改变法律责任、费用、公开边界、研究对象、样本框架或结论口径？

如果第 1 项没有明确答案，立即停止该方向并把它记录为非阻塞后续事项。如果第 5 项为是，先取得用户确认。

出现以下征兆时视为已经偏航，必须立刻回到当前里程碑：

- 为了已有数据而修改研究问题或 object map；
- 为了展示非空看板而放宽人工确认标准；
- 把自我推广解释成公众采用；
- 把 scope 标签预填成条目事实；
- 把搜索排序、互动数或 API 返回量称为流量或认可度；
- 在没有 query 快照时继续累积真实数据；
- 在单一热门视频下采集大量评论并称为多来源样本；
- 在 M5 内发送 Reddit、TikTok、X 或 Mastodon 真实请求，或提前开始 M6；
- 引入大型模型、标注平台或微服务但没有当前验收价值；
- 反复输出规划却不进行局部编辑和验证；
- 因某个新想法而停止维护已有记录和验收证据。
